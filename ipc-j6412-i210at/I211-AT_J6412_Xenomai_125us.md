# 基于 Intel I211-AT 与 J6412 的 Xenomai 125 µs 实时性评估与实施方案

## 1. 结论

在 J6412（4 核 Tremont）上使用 I211-AT，以 Xenomai Cobalt/RTDM 或经过适配的 RTnet 驱动运行实时任务，**125 µs 周期（8 kHz）在工程上可达到**。这里的“达到”应定义为：实时线程能够以 125 µs 绝对时间周期运行，并在规定负载下完成一次控制计算和一次确定性的网卡收发。

但 I211-AT 产品简介没有给出最坏中断延迟、DMA 延迟或实时性保证；因此不能仅凭 PDF 对“任何负载下永不超时”作出承诺。建议按下面三个等级理解：

| 目标 | 判断 | 必要条件 |
|---|---|---|
| 本机实时线程每 125 µs 唤醒一次 | 可以达到 | Xenomai、CPU 隔离、关闭深度节能状态、固定频率、锁内存 |
| 单机控制计算 + I211 收发在 125 µs 内完成 | 大概率可以达到 | RTDM/RTnet 快速路径、I211 中断与线程绑定、关闭中断合并和 EEE、预分配缓冲区 |
| 在所有温度、负载、固件 SMI 和网络拥塞条件下保证 125 µs 最坏时延 | 不能由该 PDF 保证 | 需要固定 BIOS/板卡、实时驱动、示波器和长时间压力测试，必要时更换专用实时网络方案 |

125 µs 是周期，不等于可用执行时间。若要保留调度和通信余量，建议把一次控制计算、输入处理和输出打包控制在 **70~90 µs** 内，剩余时间留给中断、DMA、缓存抖动和异常路径。

## 2. I211-AT 文档中与实时性有关的特性

依据 `I211-AT.PDF` 产品简介（主要为第 2~4 页）：

- PCI Express 2.1，单通道 x1，2.5 GT/s；
- 10/100/1000BASE-T，适合 1 GbE 铜缆连接；
- 支持 MSI/MSI-X，文档描述每端口最多可动态分配 5 个中断向量；
- 支持低延迟中断、接收侧扩展（RSS，最多 2 个队列）、描述符环和 DMA；
- 支持 IEEE 1588/802.1AS 硬件时间戳；
- 支持 802.3az EEE、PCIe ASPM、ACPI/APM 等节能功能；
- 支持接收/发送校验和卸载、TSO、TCP/UDP 分段、巨型帧（最高约 9.5 KB）；
- 支持 10/100/1000 Mb/s 全双工和流控。

这些特性对吞吐量和时间同步有帮助，但其中一些会增加实时抖动：

1. **EEE/LPI** 会在链路空闲后进入低功耗状态，恢复链路需要额外时间；实时链路应关闭。
2. **PCIe ASPM/L1 Substates、CPU C-State 和网卡节能** 会引入退出延迟；应关闭或限制到浅睡眠状态。
3. **中断合并、NAPI 批处理、GRO/LRO/TSO/GSO** 会把多个包合并处理，吞吐量较好，但会增加包到达时间的不确定性。
4. **RSS 多队列** 适合吞吐量扩展；125 µs 控制链路通常应使用固定队列和固定 CPU，避免跨核迁移。
5. IEEE 1588 硬件时间戳适合测量和时钟同步，不能单独把普通 Linux 网络栈变成硬实时栈。

I211 在 Linux 中通常由 `igb` 驱动支持。真正的实时性取决于驱动是否运行在 Xenomai RTDM/RTnet 快速路径；普通 `igb` + 普通 UDP socket 只能作为低延迟方案，不能当作硬实时保证。

## 3. 推荐的软件栈

### 3.1 首选：Xenomai Cobalt + RTDM/RTnet

对于 125 µs 控制周期，推荐使用与内核严格匹配的 Xenomai Cobalt 发行版和对应的 I-pipe/Dovetail 内核分支：

- 选择一个长期维护的 Linux LTS 版本；
- 按 Xenomai 官方版本矩阵选择对应的 Dovetail/I-pipe 分支；
- 不要把任意 Linux 6.x 内核、任意 Xenomai 补丁和厂商 `igb` 驱动直接拼接；
- I211 使用 `igb`，需要确认所选 RTnet/RTDM 版本已有 I211 支持；若只有普通 `igb`，需要移植 RTDM 网络驱动或改用 RTnet 支持的等价驱动；
- 实时线程使用 RTDM socket、RTnet socket 或设备专用 RTDM 接口，避免经过完整 Linux 网络协议栈。

建议先用一个最小闭环验证：实时线程定时发送固定长度 UDP/RTnet 帧，接收端立即回帧，记录本机时间戳和硬件时间戳，再逐步加入控制算法。

### 3.2 备选：PREEMPT_RT + 普通 UDP

PREEMPT_RT 配置更容易维护，普通 `igb` 驱动也更容易使用。在低负载和固定网络拓扑下，125 µs 周期通常可以运行，但网络收发、NAPI、锁竞争和系统服务仍可能让最坏时延出现几十微秒甚至更大的尖峰。若需求是“统计意义上的低抖动”，可考虑；若需求是硬实时闭环，优先使用 Cobalt/RTDM 或专用实时网络。

## 4. J6412 平台配置建议

### 4.1 BIOS/固件

在可以控制 BIOS 的前提下，建立一个固定的实时配置文件：

- 关闭 CPU 深度 C-State、C1E、Package C-State，至少先关闭 C6 及更深状态；
- 关闭 PCIe ASPM 和 L1 Substates；
- 关闭 I211 的 EEE，固定 1 Gb/s 全双工；
- 将 CPU 频率设为 Performance/固定档位，避免频率随负载跳变；
- 关闭不需要的音频、无线、SATA、USB 控制器和板载外设；
- 关闭可能产生长时间 SMI 的硬件监控、USB legacy、固件更新和自动风扇管理功能，具体以主板 BIOS 为准；
- 保留不变的 TSC/HPET 配置，并确认启动后 TSC 单调、稳定；
- 关闭 Turbo 不是绝对必要，但固定频率有利于复现实验结果；
- 关闭 BIOS 中的网卡节能和 PCIe 链路节能选项。

J6412 是低功耗平台，深度节能退出时间和固件 SMI 比高性能桌面 CPU 更值得关注。即使平均延迟很好，也必须单独测量最坏尖峰。

### 4.2 内核和启动参数

使用与 Xenomai 版本匹配的内核配置。常用方向包括：

- 启用 Xenomai Cobalt、架构本地 APIC、RTDM 和所需的网卡/PCIe 驱动；
- 关闭不需要的调试、审计、内核抢占追踪和高频日志；
- 关闭或限制 CPU 频率调节和 CPU idle 驱动；
- 启用高精度计时器，并使用稳定的 TSC 作为时钟源；
- 关闭自动负载均衡和实时核上的普通任务迁移。

一个可作为起点的启动参数示例如下，CPU 编号必须按实际拓扑调整：

```text
isolcpus=domain,managed_irq,2-3
nohz_full=2-3
rcu_nocbs=2-3
irqaffinity=0-1
nowatchdog
nmi_watchdog=0
```

这些参数只是起点，不能替代实测。可先把实时线程固定到 CPU2，把 I211 中断固定到 CPU2 或 CPU3，再比较“同核处理”和“分核处理”的最大抖动。控制计算和网卡快速路径通常应尽量减少跨核队列转移。

### 4.3 I211 网卡参数

接口名假定为 `eth0`，实际名称以系统为准：

```bash
# 关闭节能和中断合并
ethtool --set-eee eth0 eee off
ethtool -C eth0 rx-usecs 0 rx-frames 1 tx-usecs 0 tx-frames 1

# 关闭会改变包处理批次的卸载功能；逐项测量后可重新开启校验和卸载
ethtool -K eth0 gro off lro off gso off tso off

# 将队列和环形缓冲区控制在可预测范围
ethtool -L eth0 combined 1
ethtool -G eth0 rx 256 tx 256

# 固定链路（交换机必须支持）
ethtool -s eth0 speed 1000 duplex full autoneg off
```

`rx-usecs=0`、单队列和 256 描述符是测试起点，不是所有板卡的最终值。若压力下出现丢包，应逐步增大 RX/TX ring；若出现批量延迟，则优先检查中断合并和 NAPI 调度。校验和卸载是否关闭应通过实测决定，关闭后 CPU 预算不足时可保留校验和卸载。

## 5. 实时任务实现要点

实时线程应满足以下约束：

- 使用 `mlockall(MCL_CURRENT | MCL_FUTURE)` 锁定内存；
- 启动阶段预分配所有报文、对象和缓冲区，周期循环中不执行 `malloc/free`；
- 周期线程使用绝对时间等待，例如 Xenomai `rt_task_set_periodic()` 和 `rt_task_wait_period()`；
- 设置高实时优先级，例如 80~95，并将线程固定到指定 CPU；
- 周期中不进行文件、串口、日志、DNS、动态链接、普通 `printf` 或可能切换到 secondary mode 的系统调用；
- 使用固定长度报文、预分配 TX/RX 缓冲区和无锁单生产者/单消费者队列；
- 将诊断、日志和非实时网络放到 housekeeping CPU；
- 任何超时都要计数，不能在实时线程中重试阻塞操作。

伪代码结构：

```c
rt_task_set_periodic(NULL, TM_NOW, 125000); /* ns: 125 us */
for (;;) {
    rt_task_wait_period(&overrun);
    t0 = rt_timer_read();
    rx_control_frame();
    run_control_algorithm();
    tx_control_frame();
    record_short_timestamp(t0, rt_timer_read());
}
```

实际工程中还要把输入采样、输出提交和网卡事件的时间基准统一起来。若外部设备提供同步时钟，使用 I211 的 IEEE 1588 硬件时间戳做测量/校时；不要使用普通软件收包时间戳作为精确控制基准。

## 6. 抖动来源和对应措施

| 抖动来源 | 典型处理 |
|---|---|
| C-State、P-State、Turbo 切换 | BIOS 固定性能，关闭深度 C-State 和频率调节 |
| PCIe ASPM/L1 退出 | BIOS 和网卡 PCIe 电源管理关闭 |
| EEE/LPI | `ethtool --set-eee eth0 eee off`，交换机端口也关闭 EEE |
| I211 中断合并 | RX/TX `usecs=0`、`frames=1`，使用单固定队列 |
| NAPI/GRO/LRO/TSO/GSO 批处理 | RT 路径关闭，固定长度小帧 |
| 普通 Linux 网络栈 | 使用 RTDM/RTnet；不要让实时闭环依赖普通 UDP |
| IRQ 在多个核间迁移 | 固定 IRQ affinity，避免实时核被普通 IRQ 污染 |
| 内存缺页和缓存分配 | `mlockall`、预触页、预分配、固定内存池 |
| RCU、定时器和普通内核线程 | `nohz_full`、`rcu_nocbs`、隔离实时核 |
| SMI/固件后台任务 | 关闭不必要固件功能，并用示波器确认异常尖峰 |
| 温度保护和降频 | 保证散热，记录 CPU 温度和频率，避免被动降频 |
| 跨核队列和锁竞争 | 固定线程/IRQ/队列，采用无锁单生产者队列 |

## 7. 验证和验收方法

### 7.1 三阶段测试

1. **纯调度测试**：不启用网卡业务，只测 Xenomai 周期线程的唤醒延迟。
2. **网卡收发测试**：固定长度帧、单队列、满载和非满载分别测试，记录收发和往返延迟。
3. **系统压力测试**：同时运行磁盘、内存、非实时网络、CPU 压力和温度压力，观察实时核和 I211 的最大尖峰。

### 7.2 测试工具

- Xenomai `latency` 测试：周期设为 125000 ns，记录 min/avg/max 和 histogram；
- `cyclictest` 可用于 PREEMPT_RT 对照，但不能替代 Cobalt/RTDM 测试；
- `ftrace` 的 `irqsoff`、`preemptirqsoff`、`function_graph` 查找长临界区；
- `/proc/interrupts`、`/proc/irq/*/smp_affinity` 检查中断归属；
- `ethtool -S eth0` 检查丢包、RX overrun、TX timeout 和重置；
- 在实时周期起点翻转 GPIO，用示波器/逻辑分析仪直接测量周期和最大脉宽；
- 用 I211 IEEE 1588 硬件时间戳对比线上帧到达时间，区分“线程唤醒抖动”和“网络传输抖动”。

### 7.3 建议验收指标

最终指标应由项目需求定义。对第一版样机，可采用以下门槛作为工程起点：

- 8 kHz、连续 24 小时，周期丢失次数为 0；
- 正常负载下最大调度抖动目标不超过 ±5 µs；
- 压力负载下最大抖动目标不超过 ±10 µs；
- 控制计算和收发总时间小于 90 µs；
- 不允许出现 RX overrun、TX timeout、网卡复位和链路重新协商；
- 记录最大值、99.9%、99.99%、99.999% 分位数，不能只报告平均值。

上述数值是验证门槛，不是 I211 或 J6412 的官方保证。若在 24 小时测试中出现 100 µs 以上尖峰，应优先排查 SMI、深度 C-State、PCIe ASPM、IRQ 迁移和网卡中断合并，而不是继续提高线程优先级。

## 8. 风险和替代方案

1. **驱动适配风险**：I211 的主线 `igb` 驱动可正常通信，不代表它已经具备 Xenomai 硬实时语义。RTnet/RTDM 驱动必须在目标内核上实际编译、运行和压力验证。
2. **板卡固件风险**：J6412 工控板的 BIOS 可能无法关闭全部 C-State、SMI 或 PCIe 节能功能；这种情况下可达到平均 125 µs，但最坏抖动可能不稳定。
3. **交换机风险**：交换机的 EEE、流控、缓存和端口调度也会影响端到端延迟；测试时应使用已关闭 EEE 的直连或确定性交换设备。
4. **协议风险**：普通 UDP 广播/组播不适合作为严格确定性的多轴同步协议。若需求是多轴运动控制、周期小于 250 µs、并且要求确定的最坏延迟，应评估 EtherCAT、TSN 或带专用硬件时间基准的方案。
5. **时间同步风险**：IEEE 1588 能改善时钟一致性，但不消除操作系统调度和链路排队抖动；同步精度与周期确定性必须分开验收。

## 9. 推荐落地顺序

1. 固定 J6412 主板、BIOS 版本、内存、散热和 I211 芯片版本；
2. 选定一组有明确补丁对应关系的 Linux LTS + Xenomai + Dovetail/I-pipe 版本；
3. 先完成无网卡的 125 µs Cobalt 周期测试；
4. 完成 I211 单队列、关闭 EEE/ASPM/中断合并后的 RTDM/RTnet 收发测试；
5. 逐步恢复校验和卸载、交换机和实际控制算法，确认每一步的最大抖动；
6. 用 GPIO、I211 硬件时间戳和 24 小时压力测试形成验收数据；
7. 只有在目标板卡、BIOS、内核、驱动和交换机配置全部锁定后，才把 125 µs 写入产品规格。

### 最终判断

**可以把 J6412 + I211-AT 作为 125 µs Xenomai 实时控制平台的候选硬件。** 实现关键不在 I211 的千兆带宽，而在于 RTDM/RTnet 驱动路径、BIOS 节能状态、CPU/IRQ 隔离和长时间最坏时延验证。若只是把普通 Linux `igb` 驱动和普通 UDP 程序打上 Xenomai 补丁，能够得到较低平均延迟，但不足以宣称 125 µs 的硬实时保证。
